# Risk Register — FinSecure Technologies Inc.

Scales are defined in [report/04-risk-assessment.md](../report/04-risk-assessment.md). Risk rating = Impact × Likelihood, using: Low, Medium, High, Extreme.

| # | Asset | Threat | Vulnerability | Impact | Likelihood | Risk | Control Recommendations |
|---|---|---|---|---|---|---|---|
| 1 | Sensitive customer data, financial transactions | Data breaches, SQL injection, unauthorized access | Weak access controls, outdated database, lack of encryption | Catastrophic | Likely | **Extreme** | Strong encryption at rest and in transit; strict RBAC; regular patching; database activity monitoring (DAM); MFA for admins. |
| 2 | Security event data, incident response | Log tampering, delayed detection of attacks | Misconfiguration, insufficient data aggregation, incomplete log coverage | Catastrophic | Likely | **Extreme** | Regularly review SIEM configuration; ensure full system coverage; real-time alerts; integrate with IDS/IPS; recurring testing and tuning. |
| 3 | Confidential financial data (file transfer) | Data interception, unauthorized file access, weak passwords | Weak encryption settings, poor authentication, unmonitored access | Major | Likely | **Extreme** | Enforce SSH/SFTP encryption, key-based authentication, IP allow-listing, access logging; enforce a strong password policy; add a dedicated firewall for the DMZ-adjacent transfer path. |
| 4 | User credentials, network access (Active Directory) | Unauthorized access, privilege escalation, account hijacking | Weak passwords, lack of MFA, excessive privileges, outdated configuration | Doomsday | Possible | **Extreme** | Enforce MFA; apply least-privilege review; regularly audit AD configuration, logins, and changes. |
| 5 | Authentication and access control data (AAA) | Credential theft, unauthorized access, denial of service | Misconfigured authentication protocols, weak password policy | Doomsday | Likely | **Extreme** | Strong password policy; MFA; regular AAA configuration review; log and monitor failed access attempts; add a RADIUS device to the backbone. |
| 6 | Service/application configuration (network-wide) | Monitoring gaps, incident-management failure, misconfigured changes | Insecure change-control process; insufficient staff training | Doomsday | Likely | **Extreme** | Require Method-of-Procedure (MOP) approval and rollback plans for all network changes; verify staff technical proficiency; run regular penetration tests. |
| 7 | Company/product/customer information | Social-engineering attacks targeting employees | Uncontrolled disclosure of internal information | Major | Almost Certain | **Extreme** | Strict policy on public disclosure and company-name use on social media; enforce outbound proxy rules; disable USB ports on sensitive endpoints. |
| 8 | Internet/service availability | Loss of ISP link connectivity | Extended downtime affecting all services | Major | Possible | **Extreme** | Verify SLA compliance with ISPs; test regular primary→backup link failover; formal incident/ticketing process with ISPs. |
| 9 | Banking service availability | Partial or total service loss | Undetected backbone incidents; inconsistent procedure documentation | Doomsday | Likely | **Extreme** | Follow a joint FinSecure/GlobalTech communication matrix; document all incident actions; formal incident response, business continuity, and disaster recovery plans. |
| 10 | Network availability | Outdated configurations, privilege abuse | Excessive standing permissions | Catastrophic | Possible | **Extreme** | RBAC scoped to least privilege; MFA on all elevated accounts; IAM-managed permission audits; Privileged Access Management (PAM) tooling. |
| 11 | Network equipment | Equipment failure during operation | Requires physical replacement | Major | Possible | **High** | Physical/logical redundancy; preventive-maintenance compliance; critical spares inventory; vendor SLA (99.999%) and MOP for replacement. |
| 12 | Customer-facing web apps, user data | DoS/DDoS, XSS, CSRF | Unpatched software, weak authentication, poor input validation | Catastrophic | Unlikely | **High** | Secure coding practices; DDoS protection; regular patching; enforce HTTPS; input validation and output encoding; secure reverse-proxy layer. |
| 13 | Perimeter security, network traffic | Firewall bypass via misconfiguration or exploit | Outdated signatures, unpatched rules | Major | Possible | **High** | Regularly update firewall signatures; harden configuration; enforce segmentation; SIEM-integrated logging and alerting. |
| 14 | Web applications, customer data | SQL injection, XSS, CSRF | Weak WAF rule sets, misconfiguration | Major | Possible | **High** | Regularly update WAF rules; secure coding review; vulnerability testing; SIEM-integrated logging; dedicated WAF instance protecting the database tier. |
| 15 | Session data, cache performance | Cache poisoning, unauthorized access | Default configuration, weak authentication, no encryption in transit | Major | Possible | **High** | ACLs; enforced authentication; TLS in transit; periodic configuration review; access-pattern monitoring. |
| 16 | Internal network traffic | Man-in-the-middle attacks, downtime | Insecure switch configuration, lack of segmentation | Major | Unlikely | **High** | VLAN segmentation; port security; strong ACLs; anomaly monitoring. |
| 17 | Network routing, perimeter security | Traffic interception, DoS/DDoS | Weak configuration, outdated firmware | Major | Possible | **High** | Regular firmware updates; strong access controls; firewall hardening; segmented routing; anomaly monitoring. |
| 18 | Server and network equipment (facilities) | Power outage, environmental damage | Loss of power/cooling causing service interruption | Moderate | Possible | **Medium** | Tier-3 data center with dual power/cooling paths (99.982% guaranteed uptime, ≈1.6 hours annual downtime). |

*This register consolidates and reformats the original Group 3 risk assessment tables into a single, consistently structured document.*
